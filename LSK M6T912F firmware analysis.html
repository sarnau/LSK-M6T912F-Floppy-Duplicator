01

Overview

The device reads one master floppy into a bank of DRAM, then writes and verifies up to four blank floppies at once. It runs standalone from a front-panel menu, drives an optional mechanical autoloader over RS-232, and can be driven by a host PC in a remote-control mode that streams a disk image down a dedicated data channel.

Both serial links have their own dedicated references: the autoloader (a separate PIC16C57/ST93C06 device — the machine is its client) and the host remote-control protocol (the machine is the server). See §7 for the firmware-side summary.

The firmware is a single 32 KB image. At reset it copies itself into RAM, banks the EPROM out, and runs entirely from RAM — which is what makes field firmware updates (“Code loading”) possible. Every claim below was checked against a purpose-written Z80 disassembler and the manufacturer datasheets for each chip on the board.

Origin markers in the strings — Adresa = (Czech/Slovak/Croatian for “address”), controll, hystheresis — point to a Central/Eastern-European developer. Copyright banner: LSK Data Systems 1995.

Memory architecture

The 64 KB address space splits cleanly in half. Both halves are the same 0xB0-banked DRAM array: the lower half is DRAM bank 0xFF — loaded with the EPROM mirror at boot and then fixed there by OUT 0x9C,0x92, holding the running program; the upper half is a window onto image banks 0x00–0xFE that buffers the disk image.

Is 0x0000–0x7FFF really RAM, not the EPROM?

Yes — the physical part is an EPROM, but at runtime that address range is answered by static RAM. Five independent proofs:

  • 316 store instructions target addresses below 0x8000. You cannot write an EPROM with LD (nnnn),A; the machine's own variables live here.
  • The boot checksum stores then reads back. LD (0x52EF),A writes the computed sum; 0x0128 reads it back and compares to reference byte 0x52F0 = 0xC7. Storing a computed value and reading it back only works in RAM.
  • The “variable” regions are zero-filled holes in the image — classic initialized-data + BSS laid into a RAM image (e.g. 0x4A50–0x4AB0 is all 00).
  • The boot ceremony is pointless otherwise: it LDIRs the image up to RAM and bank-switches before JP 0x0100. In-place EPROM execution would just jump at reset.
  • “Code loading” requires it: field firmware updates over serial can only replace the running image if it sits in writable RAM, guarded by that checksum.

It's the same idea as a PC BIOS shadowing ROM into RAM — except here it's mandatory, not just for speed. The image DRAM and the program RAM are the same banked array — 2× 4 MB 30-pin SIMMs = 8 MB (parity-type, but the parity bit is simulated/generated rather than checked) — holding the source disk image so a master is read once and written to every target. Port 0xB0 selects which 32 KB bank appears in the 0x8000–0xFFFF window (8 MB = 256 banks). One bank is reserved: bank 0xFF is the program RAM, so the image buffer is banks 0x00–0xFE (255 banks ≈ 7.97 MB, enough to cache ≈5× 1.44 MB images). The Test dram: N kB routine sizes the installed DRAM at boot by walking banks — OUT (0xB0),A; LD (0x8000),A; CP (0x8000) — and counting those that read back.

Bank 0xFF is the program mirror

The “static RAM” at 0x0000–0x7FFF is not a separate chip — it is DRAM bank 0xFF, loaded with a copy of the EPROM at boot and then mapped low. Traced byte-for-byte at reset:

AddrCodeEffect
000ELD A,0xFF; OUT (0xB0),Aselect bank 0xFF in the 0x8000 window
0014LD BC,0x5FFF; LD HL,0x0022; LD DE,0x8022; LDIRcopy EPROM 0x0022–0x6021 into bank 0xFF (0x8022+)
001FJP image_buf+0x22run the fresh copy inside bank 0xFF's window
0022LD A,0x92; OUT (0x9C),Alatch bank 0xFF permanently at 0x0000–0x7FFF, drop EPROM
0026JP boot_init (0x0100)continue from the RAM copy

Two independent facts confirm bank 0xFF is reserved for code, not an image bank:

  • The relocation writes there. The LDIR target 0x8022 is the 0x8000 window with 0xB0=0xFF already selected, and the next instruction executes from that window — so bank 0xFF is the memory that becomes the program at 0x0000–0x7FFF.
  • Every image-bank walk stops before it. The boot DRAM sizing and the per-bank checksum loop (0x5193: INC A; CP 0xFF; RET Z) iterate banks 0x00–0xFE and terminate the instant the bank index reaches 0xFF — bank 0xFF is never sized, checksummed, or used to hold image data.

This is why “code loading” (field firmware update) can work at all: the running image lives in writable bank-0xFF RAM, so a new image can be streamed into it and re-checksummed in place.

Verified — the mapping is set-once OUT (0x9C),0x92 executes exactly once, at boot 0x0022 (the only other LD A,0x92 is 0x07EA: LD (fmt_mode),A, a RAM store). OUT (0xB0),0xFF also runs exactly once (0x0010); every later 0xB0 write loads an image bank (track_bank_a/b, or 0xFE scratch), never 0xFF. Neither the 0x9C map bit nor the bank-0xFF selection is ever re-commanded, and runtime writes leave low RAM intact: the copy loop does OUT (0xB0),A then keeps fetching from low RAM while building a ≥0x8000 pointer (0x0E49), and fdc_poll_complete pulses the same port 0x9C (0x0E→6 NOPs→0x0F, 0x475E) with the PC running straight through. A plain 8-bit register at 0x9C couldn't survive that (writing 0x0E after 0x92 would clear 0x92's high bits) — so 0x9C is an addressable per-line latch (74259-class): the boot commands the map line once, every runtime write selects a different line, and bank 0xFF stays mapped low for the whole runtime.

0x9C latch decode (verified)

The addressable-latch decode is pinned from firmware to data = bit 0, select = bits [3:1]. Bit 0 is data: update_ctrl_latch (0x0760, CP 0x01; OR 0x01) and the 0x24DD path (LD A,0x05; XOR 0x01 → 0x04/0x05) both toggle only bit 0 on a fixed select, and the FDC strobe 0x0E→0x0F differs only in bit 0. Select is the low bits, not the high nibble: 0x04 (write gate) and 0x0E (FDC strobe) are distinct runtime functions, so they must occupy different lines — only a bits-[3:1] select separates them (lines 2 vs 7); a high-nibble decode would collide them. The high nibble (0x92's 0x90, 0x2D's 0x20) is therefore don't-care. Six distinct lines are observed, all consistent with the decode:

Function derivations (firm unless noted): Line 2 = write-protect — the 0x24DD handler is the front-panel “Write protect” config screen (get_key → 0x04/0x05 → store wprot_mode → config_wprotect; string at 0x24EF). Also driven remotely: host op 0x0D (0x200B) writes a host-supplied byte to 0x9C and caches it in wprot_mode. Lines 4 & 5 = per-drive datarate select — update_ctrl_latch (0x0760) is called with A = fdc_rate_a/b (a cylinder-banded rate) and E = 0x08 (→ line 4, drive A) / 0x0A (→ line 5, drive B), setting bit0 for rate class 1 and bit2 of the drive latch (0x50/0x70) in parallel. The banded rate is read from the Special-format zone tables (fmt_geom_recs): range_table_lookup (0x092A, B=6) scans a head's 6 {start-cyl, rate} zones for the current cylinder and returns the N/L/H flag — confirming N/L/H is per-cylinder data rate (variable-rate zoned formatting). Line 6 = a static enable, not precompensation — its data bit is bit0 of drv_active_cfg, a hardcoded constant 0x2D (written once at 0x01B7, never config-changed); every consumer uses only that bit (all do AND 0x01, some force SET 0,A) and it is always 1. The same bit is fanned into the drive-control latches (0x40/0x60, active pattern 0x2D vs idle 0x0E) and written to 0x9C line 6 once at boot (0x03C2), never cleared — a permanently-asserted global enable. The real write-precompensation is a separate path: fdc_datarate_precomp (0x1141) computes it per-geometry and outputs to FDC port 0xC2 (fdc_precomp). Line 6's exact physical signal (write-gate / reduced-write-current / drive-enable) isn't determinable from firmware, but its behavior — set-once, held high — is. (The disassembly symbol was renamed from the misleading precomp_val to drv_active_cfg to reflect this.)

The map line (001) is written by exactly one instruction in the whole image (OUT (0x9C),0x92 @ 0x0022); no runtime write ever selects it. Not derivable from firmware: the physical A0–A2 ordering (permuting relabels the line numbers but preserves the grouping), which Q-pin drives which board signal, and the meaning of the don't-care high bits — all need the schematic.

Boot sequence

A 38-byte stub at 0x0000 runs from EPROM, relocates the program into RAM, then hands off. This is a genuine ordered sequence, so the steps are numbered.

10000Init 8237 DMA (OUT 0x88,0xA0 / 0x8D,0x8F=0x0F), set SP=0x8000, select DRAM bank 0xFF (program-RAM window) via OUT 0xB0,0xFF; then OUT 0xC0,0xFF (a separate one-shot control-latch init — see port map)
2001DLDIR copies EPROM 0x0022–0x6021 → bank 0xFF at 0x8022, then JP 0x8022 (runs the copy in bank 0xFF's window)

Maskable interrupts (IM 1) vector through 0x0038 → JP 0x45DB, the FDC result-phase handler: it reads which controller interrupted (port 0x94) and pulls the 7-byte result phase from each of the four FDCs.

06

Floppy subsystem

Four FDC37C65C controllers, one per drive, are commanded by polled PIO but fed their bulk sector data by the 8237 — one DMA channel per controller. To write four disks at once, the firmware arms all four channels against the same track buffer and lets the DMA engines clock it out concurrently.

Command and data primitives

  • Write bytes — 0x457F: poll MSR (AND 0xC0;CP 0x80 = RQM set, DIO clear), then INC C;OUTI to the data register at base+1.
  • Read result phase — 0x46F1: wait RQM (BIT 7), test DIO (BIT 6), INI each byte; the ISR pulls all four 7-byte result phases.
  • DMA arm — 0x4401: select channel, clear flip-flop (OUT 0x8C), set mask/mode (0x8A/0x8B), stream address + count.
  • Precomp / data rate — 0x0980: 250 kbps (DD) or 500 kbps (HD), written through 0xB1/0xC2/0xC3.
  • Format — 0x1CEC: builds a FAT12 boot sector from a ROM template at 0x3305 (OEM “Jumbo”, “Non system disk”) and stamps the 0x55AA signature at 0x81FE.

07

Serial & protocols

Two independent Z80 SIO channels at 9600 baud (×16 clock from the 8253); the autoloader channel is 8N1 and the host channel switches parity per operation (boots 8O1). Fully polled (no interrupt-driven ring buffers). Channel A talks to the autoloader; channel B is the host command link. A third, separate channel (ports 0x90/0x94/0x9C, 0xAA55-framed) carries bulk image data.

Autoloader — the machine is the client (disk-handling mechanism)

The main board does not drive the insert/eject motors directly. The autoloader is a separate mechanical unit with its own controller, and channel A (0xD0/0xD4) is the link that commands its motors and reads its sensors — insert, accept, reject, calibrate, and a status byte encoding the mechanical state (hopper empty, disk-in-drive, jams, bin full, eject timeout). It sends single ASCII commands and expects X (ok) / E (error) / ? (unknown); dispatcher 0x13D9 flushes the receiver, sends the byte, checks for 'X'.

Host remote control — the machine is the server

The two serial links have opposite roles: on the autoloader link the machine is the client (above); on the host link (0xD8/0xDC) it is the server. Entered via the “Remote controll” menu, dispatcher host_dispatch (0x1E0B) is a server loop — it shows a blinking . heartbeat, reads a 4-byte packet {lead byte (read but unused), opcode, 16-bit LE parameter}, dispatches by opcode, and replies X (0x58 ack) / E (0x45 bad-packet NAK) plus a binary status byte (0x00 ok; 0x90/0xA0/0xB0 = command error / transfer failed / not-proper-image). A host PC can drive the whole duplication cycle remotely.

08

UI & features

Four front-panel keys — Next (0x08), Previous (0x04), Exit (0x02), Enter (0x01) — plus an audio beeper. Menus run on a generic driver, menu_run (0x522F): each menu is two parallel null-terminated pointer lists (a draw proc and a do proc per item); Next/Previous scroll and redraw, Enter runs the item's action, Exit returns. Two-choice screens put one option per LCD line with an …EXIT / …ENTER hint. Holding a key at power-on enters the Config menu; the beeper gives key-click and error/alert tones (port 0xF0).

Display — Hitachi HD44780 (2-line)

Port 0xE0 = instruction register (RS=0, write command / read busy on bit 7), 0xE8 = data register (RS=1, write character; IN (0xE8) also reads board-ID 0x55). All writes go through lcd_byte_out (0x4C43), which busy-waits (lcd_wait_busy) then OUT (C),A with C = 0xE0 (command) or 0xE8 (data). lcd_init (0x4B99) is a textbook bring-up:

Config & provenance

Configuration lives in the 0x31xx RAM block and is persisted to a small bit-banged serial EEPROM (helpers at 0x2ACB / 0x2B3E), re-saved whenever the config wizard completes. The boot checksum validates it; corruption forces “Run config again”.

Open questions

One genuine unknown remains (the board photo + datasheets resolved the other two).

  • Port 0xC0's function Hardware. Written 0xFF exactly once at boot (0x0012, alongside the 0xB0 bank latch) and never read or re-written. Narrowed: the whole 0x40–0x70 / 0xC0–0xC7 range is write-only (verified — zero IN reads; all inputs come from 0xF0 and the bulk channel), so 0xC0 is a write-only output latch in the drive/FDC-control group (with 0xC2 precomp, 0xC3 rate, 0xC6 drive-sel-b) — not a configured-PPI input port (ruling out the “0xFF = all-input mode-word” reading). Its chip-select comes from the board's decode logic — GAL20V8B (U5) / PALCE20V8H (U68) / MC74HCT138 (U56/U59/U60) (per the board designator map in PCB_INFO.md; note U57 is the EPROM, not a decoder). 0xFF is an all-ones idle/deselect init. What's not determinable from the ROM or the single top-side board photo is the exact latch it drives — that needs the schematic, a back-side/inner-layer view, or continuity probing (find the decode output that asserts on /IOWR with A7..0 = 0xC0).

Resolved during analysis

  • Serial controller = Zilog Z80 SIO/0 Resolved (Z0844006PSC), not an 8251 — confirmed by the board photo, the Zilog Z8440/Z84C40 SIO datasheet (datasheets/Zilog Z0844006PSC SIO.pdf, in the repo — Z0844x06 = 6 MHz Z80 SIO, SIO/0 bonding), and the firmware's SIO register model: Tx via RR0 bit 2, Rx via RR0 bit 0, data port = control with A2 cleared (RES/SET 2,C), errors from RR1 (WR0-ptr=1, mask 0x70), WR0=0x30 error-reset. One SIO carries both channels (A = autoloader 0xD0/D4, B = host 0xD8/DC); the 8253 supplies the external clock in ×16 mode (153,846 Hz ÷ 16 ≈ 9600 baud). (§2, §5)
  • Parallel I/O = a single µPD71055 PPI Resolved — no Z8420 PIO (an earlier mis-assumption from a spurious datasheet, since removed). The 0x40–0x70/B0/C6 write-only latches are PPI ports and/or discrete 74HCT373s; the firmware's write-only usage doesn't reveal the exact split, but the parallel-interface chip is the PPI. (§2)
  • 0x9C is an 8-line addressable latch Resolved (decode data = bit0, select = bits [3:1]) — line 1 EPROM/RAM map, line 2 write-protect, lines 4/5 per-drive datarate, line 6 static drive/write enable, line 7 FDC result-read strobe (§3). Residual (still needs the board): the physical A0–A2 ordering and which board signal each line drives.
  • 0xB0 Resolved is a flat 8-bit DRAM bank latch — no drive-select field; drive UNIT/HEAD select is in the FDC HD/US command byte. (§5; internals §B)
  • 0xE8 / 0x55 Resolved is an LCD presence/health self-test with a headless fallback, not a board-ID strap.
  • Host opcode table Resolved fully mapped: control opcodes 0x09–0x0F plus a duplication-run fall-through (0x07 = BP, 0x01–0x06/0x08 = FDD). (internals §D)
  • fmt_param_tbl (0x326E) Resolved declares 8 standard DOS formats but is dead/unreferenced — verified that no code (including the download loader) reads it. (internals §B)

Method. Disassembled with a purpose-written Z80 disassembler (full CB/ED/DD/FD coverage), cross-referenced against the on-board datasheets, and verified by reading the actual primitives — not pattern-matched from a distance.
