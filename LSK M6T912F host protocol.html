LSK M6T912F — Host Remote-Control Protocol

The second serial link turns the duplicator into a server: a host PC can drive the whole duplication cycle remotely — download an image, set up a format, run a pass, or upload and execute code — while the machine services requests and reports status.

Everything here is FW proven from the disassembly. Unlike the autoloader link, the host protocol was not observed on the wire — there is no independent ground-truth column. See the main analysis, internals, and autoloader reference.

Two links, opposite roles On the autoloader link the machine is the client (it issues S/C/I/A/R). On the host link it is the server — the host PC issues the commands below.
A Serial link B Server loop & packet C Opcode table D Bulk operations
A

Serial link

  • Z80 SIO channel B, ports 0xD8 (data) / 0xDC (control). The autoloader link is the other channel, A, at 0xD0/0xD4.
  • 9600 baud (×16 SIO clock from the 8253, 153 846 Hz ÷ 16). 8 data bits, switchable parity (boots 8O1); the autoloader link is fixed 8N1. Init is an OTIR of a WR-register blob (host_ser_blob*, applied at 0x4E03).
  • Primitives: host_tx (0x4E9D, spin on TxRDY), host_rx (via 0x4EAD, RxRDY + timeout).
B

Server loop & packet

host_dispatch (0x1E0B) — entering host mode sets host_mode = 1 and drops into the wait loop:

  • Show a blinking idle marker — a . that self-modifies to ! and back (XOR 0x0F on the character cell) so the operator sees the link is alive.
  • Read a 4-byte command packet (host_read_packet 0x1DF3). A receive error → send 'E' (NAK) and re-poll.
  • Store op_word = opcode, run_count = parameter, dispatch (0x1E37 onward), reply, loop.

D

Bulk operations

Image download — 0x0A (host_op_image_dl 0x1E37)

  • ACKs with 'X', resets counters, shows "wait for data", then waits for an 0xAA55 sync word (bulk_sync_aa55 0x2196).
  • Reads a stream of records, each re-synced with 0xAA55. A record starts with a type byte: bit 7 = last-record flag, low 7 bits = type (type 1 = track/geometry record).
  • Track data streams straight into the banked DRAM image buffer (OUT 0xB0 selects the bank); a geometry header and checksum are validated, then image_present is set.

Disk-write / format setup — 0x0D (host_op_disk_write 0x1FC6)

Streams a small parameter block and echoes each byte: cfg_flags + unit, a write-protect byte (→ 0x9C line 2 + wprot_mode, 0x200B), an err_recovery byte, then a 24-byte per-head zone table written to hrd_hd0. A host can thus define a variable-rate "Special" format remotely — the same zoned per-cylinder data-rate tables the front-panel Special-format menu builds. Clears image_present.

Load & execute — 0x0F (host_op_load_exec 0x206F)

code_loader (0x21A9) prints "Code loading", LDIR-copies a 256-byte bootstrap loader (dl_code) into RAM at 0x7800, and JPs into it. The relocated loader then pulls the new image over the bulk parallel channel — not the SIO: port 0x90 = data, port 0x94 bit 6 = data-ready, with a per-byte handshake toggled on the 0x9C latch (0x0E assert / 0x0F deassert).

Download protocol (dl_code, running at 0x7800):

  • Sync on a ramp — 16 ascending bytes 0,1,…,15 then 16 descending 15,…,0; any mismatch restarts.
  • Header — three 16-bit words: byte count, destination address, entry address.
  • Payload — stream count bytes into the DRAM staging bank 0xFE at 0x8000, accumulating an additive checksum.
  • Verify — read the expected checksum byte; mismatch → abort (RET NZ).
  • Commit — LDIR the staged bytes to the header's destination, then JP (HL) into the entry point.
Arbitrary-code-execution path Because the running firmware lives in writable bank-0xFF RAM, a downloaded image can rewrite the firmware in place and re-checksum it — the whole reason for the shadowed-ROM / bank-0xFF design. The same code_loader is also reachable from the front-panel Config → "Code loading" menu, so it isn't host-only. By design it is an arbitrary-code-execution path; the dead fmt_param_tbl DOS-geometry table (0x326E) is the kind of thing an externally-supplied loader module would consume.

I/O-vector retargeting

Byte-level I/O (get/put/beep) goes through three RAM vectors — iovec_out 0x52C9, iovec_poll 0x52CB, iovec_beep 0x52CD — dispatched via 0x4D89/0x4C43/0x2766. The same call sites serve the local keypad, the autoloader, or the host depending on the installed vectors; the 0x0B (enter-run) opcode rewrites all three and jumps to the shared run loop, so a host-initiated run reuses the identical duplication code path as a front-panel run.
