LSK M6T912F — Subsystem Internals

Byte-level drill-downs into the four load-bearing subsystems: the duplication engine, the FDC command engine, the HRD diagnostics + 8253 timer, and the serial protocol handlers. Companion to the main analysis; every excerpt is verbatim from the ROM.

Confidence: Verified read from code · Uncertain flagged. See the main analysis for the hardware map.

Correction carried into the main doc The drill-downs found that the DRAM image-buffer bank is selected by port 0xB0, not 0x9C — proven by the boot DRAM-sizing loop (OUT (0xB0),A; LD (0x8000),A; CP (0x8000) at 0x03EE) and by every image-window access in the copy/verify/format paths. Port 0x9C is a separate control/mode latch. The main analysis and port map have been updated.

A

Duplication engine

The copy engine is a cooperative phase machine, not a bitfield sequencer. Two words of state drive it: an operation word at 0x3134 and a current-phase-handler pointer at 0x3131 (loaded from a media-indexed jump table at 0x1444).

The RD+ family (Read-source then FWV/WV/FW/W) is a single meta-phase 7 plus a sub-mode selector 0x314F = 1/2/5/6. Launcher 0x25E6 sets phase 7 and clears the image-present flag to force a fresh read.

Engine phases

  • Read source (0x11B4) — reads the master once into the DRAM image (bank paged via OUT (0xB0)), autoloader-aware. 32-bit position counter at 0x3269/0x326B. Image integrity check at 0x51A9 sums 0x8000–0xFFFF and stores the complement at 0xFFFF.
  • Format (0x1CE2) — builds a FAT12 boot sector from ROM template 0x3305 ("Jumbo" OEM, "Non system disk"), stamps 0x55AA at 0x81FE, then formats all targets.
  • Write (0x08DE) — parallel DMA: each target FDC has its own state block (0x4AEB/0x4B06) and 8237 channel; all stream the same track buffer at once.
  • Verify / compare (0x0E46) — DMAs the written track back into a fixed low-RAM scratch at 0x5800 and CPI-compares against the DRAM image; mismatch sets ERR_A/ERR_B.

Batch & autoloader

Loop tail 0x1090 decrements the run counter 0x313D; on completion the accept/reject sequencer 0x10D2 diverts a good copy to the accept bin ("ACCEPT") or a failed one to reject. Because each target owns its channel and state block, a target that fails verify only sets its group's error bit and is rejected — the others continue. Uncertain no separate per-target "alive" mask beyond the two group bits was found (fits a 2-media-group design).

B

FDC command engine

Command and result phases use polled PIO (0x457F write, 0x46F1 read); bulk data moves by 8237 DMA. Each controller pair has a RAM state block; commands are issued with an LD SP,IX / POP trick that rapid-loads the block, arms DMA, and streams the command to the FDC data register.

Bulk DMA — µPD8237A @ base 0x80 [V]

Register map confirmed against the µPD8237A datasheet — standard layout, one channel per FDC (ch0=0x80, ch1=0x82, ch2=0x84, ch3=0x86):

PortRegisterPortRegister
80/81ch0 address / count88command (W) · status (R)
82/83ch1 address / count89software request
84/85ch2 address / count8Amask one channel
86/87ch3 address / count8Bmode
8Cclear byte-pointer flip-flop8Dmaster clear (W) · temp (R)
8Eclear all masks8Fwrite all four mask bits

Boot init @0x0000: master clear (OUT 8D), mask all (OUT 8F,0x0F), command 0xA0 (controller enabled, fixed priority, DACK active-high, extended write). Per-transfer arm is dma_arm_channel 0x4401 (via wrapper 0x43EC, which SP-swaps drive_blk+8..11 into the DMA address/count): BIT 7 of the channel selector picks the ch0/ch1 branch (0x441B: A==0x01→ch0 C=0x80, else ch1 C=0x82) or the ch2/ch3 branch (0x4408: A==0x81→ch2 C=0x84, else ch3 C=0x86). Each branch writes the channel-index | transfer-type byte to the single-mask (8A) and mode (8B) registers — mode 0x08|ch = read-transfer (memory→FDC = disk write), 0x04|ch = write-transfer (FDC→memory = disk read) — writes the two-byte address then count through the port in C, then rewrites 8A to its final enable state. The 8C clear-flip-flop is pulsed only in the ch0/ch1 branch (before its 16-bit writes); the ch2/ch3 branch omits it and relies on the flip-flop staying balanced — boot master-clears it (8D) and each arm does exactly four byte-writes. The channel address is 16-bit only (A0–A15); the DRAM image bank above it is paged separately by port 0xB0. DMA only ever targets image banks 0x00–0xFE; bank 0xFF is reserved as the program-RAM mirror (boot LDIRs the EPROM into bank 0xFF at 0x8022, then OUT 0x9C,0x92 fixes it at 0x0000–0x7FFF — see main §3), which is why the bank checksum loop at 0x5193 (INC A; CP 0xFF; RET Z) walks 0x00–0xFE and stops at 0xFF. The map is set-once: OUT (0x9C),0x92 and OUT (0xB0),0xFF each execute exactly once (boot), and runtime 0x9C strobes (fdc_poll_complete 0x0E→0x0F @0x475E) run with the PC fetching straight through from low RAM — so 0x9C is an addressable per-line latch and bank 0xFF stays mapped low.

Seek family & SENSE INTERRUPT (auto-issued)

  • RECALIBRATE 0x07 (0x39A0) and SEEK 0x0F (0x42DD, target cylinder in register C → NCN byte).
  • After a seek/recal interrupt, the ISR path 0x462D recognizes the pending opcode and automatically issues SENSE INTERRUPT STATUS (0x08), capturing ST0 + PCN.
  • Data rate / write-precomp go through the FDC register interface at 0xB1/0xC2/0xC3 (250 kbps DD, 500 kbps HD). The step-timing/SPECIFY equivalent is the parameter block at 0x3CD3 Uncertain — its opcode byte is runtime-computed, not a literal 0x03.

No base-address load of 0x326E exists anywhere in the 32 KB ROM (an exhaustive pointer search returns only two false-positive hits, both bytes inside other instructions). The download/code-load loader (code_loader 0x21A9 → dl_code 0x21CE→0x7800) — the natural “STIBG11 loader module” — was checked directly and never touches it either; it is a serial firmware downloader (sync preamble → address/count → stream into image_buf). The geometry the engine actually uses lives in format_desc (0x52DD), assembled from the config-menu selection via media_cfg_index (0x520A): form-factor / density / mode bits → 0–7 index → phase handler + FDC flags + init_format_geom (0x5101). The FAT12 boot sector is built from fat12_template (0x3305), not from this table. Most likely a leftover from an earlier build.

C

HRD diagnostics & the 8253 timer

The 8253's counter 0 (mode 3, ÷13) produces 153 846 Hz — both the Z80 SIO baud clock and the cascade clock into counters 1 & 2, which are used as interval timers. Counter 1 (0xA4) times head 0; counter 2 (0xA8) times head 1.

Spindle RPM — genuine interval timing (0x37DB → 0x2E72)

38BE  LD A,0x74 ; OUT (0xAC),A   ; counter1, 16-bit, mode 2
38C4  LD A,0xFF ; OUT (0xA4),A x2 ; preload 0xFFFF
...   wait one index-to-index revolution (sensor bit on 0xF0)...
3908  LD A,0x84 ; OUT (0xAC),A    ; latch counter
390C  IN A,(0xA8) x2              ; read residual -> HL
3917  SBC HL,DE                   ; elapsed ticks = 0xFFFF - residual
; then:  RPM = 0x008CD9B1 / ticks  =  9,230,769 / ticks

9 230 769 = 60 × (2 MHz ÷ 13) — an exact integer match that pins the counter clock and the 2 MHz 8253 input, which the board derives as 32.000 MHz ÷ 16 (the board carries 32 MHz + 48 MHz crystals). Checks: 300 RPM → 30 769 ticks; 360 RPM → 25 641 ticks. Comfortably inside 16 bits, which is exactly why the ÷13 clock is cascaded rather than the raw 2 MHz.

The alignment-diagnostic suite (no ADC)

The HRD diagnostics menu (hrd_menu 0x1540) offers five measurement types, all read from a factory alignment diskette and computed in software from the FDC read stream — there is no ADC. The selected type (hrd_test_idx, 0–4) maps 1:1 onto a record of the ROM table hrd_test_tbl (0x3186):

idxtest (ROM label)scale Kunit
0Radial alignment (3 tracks)422µm
1Eccentricity422µm
2Head azimuth696arc-min (')
3Positioner “hystheresis” (sic in ROM)422µm
4Spindle motor speed1RPM (raw)

Each 5-byte record is { scale K : word, handler address : word, result mask : byte }; the handler is reached by a computed jump (PUSH DE; RET, 0x2CED) and points to the per-test LCD formatter (hrd_disp_radial/_ecc/_azimuth/_positioner, and the shared show_rpm_suffix for spindle). These fix the displayed units: radial/eccentricity/positioner in µm, azimuth in arc-minutes ('), spindle in rpm.

Measurement pipeline (hrd_radial_measure 0x2D5B): seek the alignment track and capture four read windows into the image buffer — head 0 reads A/B at image_buf+0x0000/+0x2000, head 1 at +0x4000/+0x6000. hrd_find_burst (0x3008) scans each window for the sync burst (three bytes summing to 0xFF, ×7) and returns its byte offset. The per-head result is the difference of the two burst offsets (SBC HL,DE), cancelling common-mode timing and leaving the radial displacement. This is repeated 10× and passed through hrd_median_filter (0x3084, bubble-sort + average the middle samples) to yield the stored hrd_hd0/hrd_hd1.

The display scale is a ROM constant Resolved — hrd_show_scaled (0x2CEE) computes displayed = raw × K / 10000 (mul16, then ÷ 0x2710), where K is hrd_test_tbl[test].scale. That table is never written by any code — it is static, ROM-initialised — so the geometric→display scale is a firmware constant, not a value embedded in the captured disk as previously suspected. The three radial-displacement tests share K = 422 (µm), azimuth uses K = 696 (angular), spindle uses K = 1 (raw RPM — derived separately via the 8253, above).

The capture reuses the normal FDC read path; the 0x9C 0x0E→0x0F strobe seen during it is just the general fdc_poll_complete (0x472D) result-read pulse — one line of the 0x9C addressable latch (decode data = bit 0, select = bits [3:1]: 0x0E→0x0F is a 0→1 edge on select-111/line 7; other lines 001 EPROM/RAM map, 010 write-protect, 100/101 datarate, 110 static enable). See main §3.

D

Serial protocol handlers

Both links are polled. Primitives: TX 0x4E42 (spin on TxRDY=bit2), RX 0x4E5A (RxRDY=bit0, with timeout). Autoloader wrappers use 0xD0/0xD4; host wrappers use 0xD8/0xDC.

Autoloader client — command + ACK (0x13D9)

13D9  IN A,(0xD0) x3      ; flush stale RX
13DF  CALL 0x4E91         ; reset cmd-reg (0x30)
13E2  CALL 0x4E99         ; TX command byte in B
13E5  CALL 0x4EA1         ; RX reply -> B
13ED  LD A,0x58 ; CP B    ; reply == 'X' ?  (A=0 ok / 1 timeout / 2 wrong)
  • Only S, C, I, A, R are ever transmitted. Verified by exhaustive scan — this ROM never issues the autoloader O (version) or V (cycle-count) commands. The cycle count is an internal 32-bit counter at 0x3269/0x326B, bumped once per successful INSERT.
  • S returns two ASCII hex characters (e.g. "0B"); 0x13FB decodes them to the single status byte matched in the ground-truth table.
  • Connection probe (0x0220) pings with R: a pure RX timeout (0x314C=0) → "AUTOLOADER NOT CONNECTED"; a reply with framing/parity bits → "COMMUNICATION ERROR".

Host remote control — the machine is the server

The two serial links have opposite roles: on the autoloader link the machine is the client (it issues S/C/I/A/R, above); on the host link (USART 0xD8/0xDC) it is the server. A host PC can drive the entire duplication cycle remotely — download an image, format/write, run a pass, or upload and execute code — while the machine services requests.

host_dispatch (0x1E0B) is the server loop: it shows a blinking '.' heartbeat (toggled ./!), polls the host link for a command packet, dispatches by opcode, replies, and loops.

  • Command packet — host_read_packet 0x1DF3, 4 bytes: {lead byte → E, opcode → D, 16-bit LE parameter → HL} — the lead byte is read off the wire but never used or validated (a sync/reserved byte); a valid packet sets op_word = opcode and run_count = parameter.
  • Replies — 'X' (0x58) = ACK/OK, 'E' (0x45) = bad-packet NAK; a pure RX timeout just re-polls (heartbeat). Handlers additionally return a binary status byte: 0x00 ok; 0x90 / 0xA0 / 0xB0 = command error / transfer failed / not-proper-image.

Duplication-run opcodes — anything not matched above falls through to host_op_begin_run (0x20E3), where the opcode itself becomes run_status (the operation mode); there is no unknown-opcode reject path:

The I/O-vector mechanism (0x4D89/0x4C43/0x2766 dispatch through 0x52C9/CB/CD) retargets identical byte-I/O call sites between local keypad, autoloader, and host — the 0x0B opcode rewrites all three vectors and jumps to the shared run loop.

Config storage — CAT24C02 I²C EEPROM (eeprom_transfer 0x2735)

eeprom_transfer is a bidirectional block transfer to the CAT24C02 (bit-banged I²C on port 0xF0), despite the name — the direction is a parameter:

RegMeaning
Adirection — 0 = load (EEPROM → RAM), non-zero = save (RAM → EEPROM)

Save writes one byte per I²C transaction (start + device + word-addr, one data byte, stop; INC address each pass — honours the per-byte write cycle). Load is a single sequential read (start, addr, restart, then B bytes: ACK each, NAK+stop the last).

Provenance. Each subsystem was traced independently, then cross-checked; the one cross-cutting correction (0xB0 vs 0x9C for DRAM banking) was verified against the boot DRAM-sizing loop before being folded into the main analysis. Uncertainties are marked inline. Register-level confirmation used the SMC FDC37C65C, µPD8237A DMA, µPD71055 PPI, 8253 PIT, Z80 CPU and HD44780 datasheets — the µPD8237A confirmed the 0x80-base DMA register map and the one-channel-per-FDC layout.
